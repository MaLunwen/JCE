## What was added, and why each language

The Lua director (`resources/assets/scripts/es_director.lua`, generated by
`build/gen_director.py`) already ran the whole diorama. Nothing was taken away
from it. Three entities were added, each owning work the director does **not**
do, so no two scripts write the same field of the same component:

| entity | language | `scriptPath` | owns | the director owns |
|---|---|---|---|---|
| `Fireflies` | Python | `scripts/es_fireflies.py` | `Firefly_*` **transform + particle colour** | `emitting` |
| `Campfire` | Java | `scripts/EsCampfire.java` | **`CampfireLight2`** | `CampfireLight` |
| `FlowerSway` | C++ | `scripts/EsFlowerSway.jcecpp` | `flower_*` **rotation** | `MeshRenderer.visible` |

Each was picked because the scene was actually missing it:

* **Fireflies never moved.** Twelve `ParticleEmitter` entities on a fixed ring;
  `es_director.lua` only ever calls `particle_set_emitting` on them. They were
  twelve motionless lamps. Now they drift on small ellipses around their
  authored positions and pulse warm yellow-green, each on its own phase.
  Python because it is low-rate ambience policy: 12 entities, two calls each.
* **`CampfireLight2` was driven by nothing at all.** `gen_scene.py` authors two
  campfire point lights and the director resolves only the first
  (`ids.fire = jce.find_by_name("CampfireLight")`); `CampfireLight2` appears in
  no line of the director. It therefore never flickered and — worse — never
  went out in the rain, so a rainy camp was lit by a steady point light with no
  visible source. The Java script reads the director's **live** intensity with
  `compGet(fireA, "Light")` each frame and mirrors it at 0.62 with an offset
  phase, so "rain douses it" and "the season tween moves it" come for free
  rather than being a second copy of `is_raining()`.
* **102 flower cards never swayed** while the wind ribbons blew and the grass
  swayed in-shader. C++ because this is the one script with an honest
  performance argument: ~6100 `set_rotation` calls per second at 60 Hz, which
  in an interpreter is 6100 dispatches and 6100 marshalled argument tuples.

### The repair in `gen_director.py`

`es_director.lua` says "GENERATED by build/gen_director.py — do not edit by
hand" and **had been edited by hand**. Regenerating it dropped a 15-line block
that existed only in the emitted file: the *first-frame audio priming* that
zeroes every looping voice on the first update (without it the first session
blasts at authored volume until the mute button is pressed). It has been put
back **into the generator**, so the emitted file is now strictly a superset of
what was on disk:

```
$ diff director_before.lua resources/assets/scripts/es_director.lua | grep -c '^<'
0
$ diff director_before.lua resources/assets/scripts/es_director.lua | grep -c '^>'
22
```

Anyone regenerating before 2026-08-16 would have silently lost that block.

### `main.c` — the four insertions

1. `es_script_langs_register()` as the **first statement** of `es_app_init`,
   before `app_init()`. The startup scene's `Script` components are
   instantiated inside `jce_runtime_create()`, so a language registered after
   that is a language every entity has already been refused by.
2. `es_script_probe_init(s_scene)` after `app_init()` — the probes are scene
   entities and cannot be resolved before the scene exists.
3. `es_script_probe_update(s_scene, dt)` in the update.
4. `es_script_probe_report("exit")` as the first statement of `es_app_exit`.

## How each language gets selected — no `JCE_SCRIPT_LANGUAGE`

The runtime asks `jce_script_vm_language_for_path()` per `Script` component
and stands up one VM per language. `.py` is claimed by
`jce_script_vm_python_register()`, `.java`/`.class` by the Java backend's.
`JCE_SCRIPT_LANGUAGE` is a **whole-process** override and is never set here —
it could not work for a scene with four languages.

**SUPERSEDED 2026-08-16 — `.escpp` is now `.jcecpp` and the engine owns it.**
See *Known gaps* #2 below. The paragraph that follows is kept because it is the
measurement that motivated the engine change, and because the old form still
resolves (the whole stored string is the first candidate tried).

**`.escpp` was this project's own invention and it was the sharpest edge hit.**
The cpp backend claims no extension on purpose (its instantiate path is a
class name resolved by exact `strcmp` through a module registry, not a file),
so a `Script` component naming a C++ class resolves to *no language* and is
refused. The only per-entity way through, with no engine change, is for the
project to claim an extension for the already-registered `cpp` language and to
name its class after the **whole** stored string:

```c
jce_script_vm_cpp_register();                       /* language first  */
jce_script_vm_cpp_add_module(es_flower_sway_module());
jce_script_vm_register_extension("escpp", "cpp");   /* the project's claim */
```
```cpp
JCE_CPP_SCRIPT_CLASS(EsFlowerSway, "EsFlowerSway.escpp")
```

Two known consequences: the editor's Script inspector shows the amber "no
language claims this extension" for it (the offline catalog cannot know about
a claim made at runtime), and editor Play cannot run it at all.

## Building it

**SUPERSEDED 2026-08-16 — the SDK path now works.** When this was written
the SDK shipped nothing from `scripting/` (no `jce_script_api` import library,
no `jce_script_vm_*` archive, no `jce_script` Python package, no compiled Java
classes, and `JCEConfig.cmake` exported no target for any of them), so
`python scripts/jce.py app elemental_serenity` — `find_package(JCE)` against
an installed SDK — could not enable any of it. `scripting/cmake/` now installs
that layer and `JCEConfig.cmake` includes the generated `JCEScripting.cmake`;
the SDK offers the SAME target names this tree uses (`jce_script_vm_python`,
`jce_script_api`, … are aliases of `JCE::ScriptVmPython`, …), so the branch
below is now a convenience rather than the only door. **An SDK produced before
2026-08-16 still ships nothing — rebuild it.** See `scripting/README.md`,
section *Out-of-tree, against an installed SDK*.

The in-tree build, unchanged, through a branch appended to this project's
`CMakeLists.txt` and a gate added to the engine's root one:

```
cmake -S ../.. -B <build> -DJCE_BUILD_INTREE_ES=ON \
      -DJCE_BUILD_SCRIPT_JAVA=ON -DJCE_BUILD_SCRIPT_VM_PYTHON=ON \
      -DJCE_BUILD_SCRIPT_API_SHARED=ON
cmake --build <build> --target ElementalSerenity
```

with `JAVA_HOME=D:\Java21\openjdk-21`. The exe lands in `<build>/release/`
with `jce_script_api.dll`, `jce_script_java.dll` and `jce_project.json` staged
beside it, and a **real** embedded PAK (`jce_add_pak`, not the one-byte stub —
see below).

Turning a backend off is safe and loud: each is `if(TARGET ...)` with a
`message(WARNING)` naming the script that will be refused.

### Two ordering traps, both hit, both silent without the warning

* `add_subdirectory(elemental_serenity)` was first placed beside
  `JCE_BUILD_INTREE_MEADOW` — **above** `add_subdirectory(scripting)`. Every
  `if(TARGET jce_script_vm_python)` read FALSE, the configure was green, and
  the app linked no backend at all. Only the three warnings caught it. The
  gate now sits after `scripting/`, like `tools/gpu_task`.
* `add_subdirectory(editor)` had the same problem and it is now fixed in the
  root `CMakeLists.txt` (committed): `scripting/` moved above `editor/`.

### The packaged path, and the cook flag that would have broken it

The in-tree branch uses `jce_add_pak()` rather than the one-byte stub PAK, so
the run that proves four languages work is a run against a real cooked+packed
archive. That matters because of this, measured:

```
$ jce_cook --batch resources/assets <out>              # NO --preserve-names
$ ls <out>/scripts
EsCampfire.jceasset  es_director.jceasset  es_fireflies.jceasset
```

Without `--preserve-names`, every script loses its extension —
`scripts/es_fireflies.py` becomes `scripts/es_fireflies.jceasset`, which
resolves to no language. `jce_add_pak()` passes the flag; a hand-rolled cook
step would not, and the result would be a scene that works from loose files
and is silently dead in the shipped build. With the flag:

```
$ ls <out>/scripts
EsCampfire.java  es_director.lua  es_director.lua.deps.json  es_fireflies.py
```

`jce_pak` stores `scripts/EsCampfire.java` **lowercased** as
`scripts/escampfire.java`. That is not a defect: `jce_archive_path_id()`
lowercases on lookup too, and the packaged run below loads it. It is the first
capitalised asset this project has ever had — Java's class-name-is-file-name
convention — so it is worth knowing.

## Evidence — counted, not asserted

Each script writes its own counters into a transform-only probe entity
(`EsLuaProbe` / `EsPyProbe` / `EsJavaProbe` / `EsCppProbe`, authored by
`gen_scene.py`): `x` = `on_start` count, `y` = `on_update` count, `z` =
entities resolved by name. `src/es_script_probe.c` reads them back every frame
and prints the table every 10 s and at exit.

A transform and not a log line, because a log line proves `on_start` and
nothing proves `on_update` is still being delivered at frame 4000 without
printing 4000 lines — and because **a C++ module has no log at all**
(`jce::script::Api` is the wrapper over `scripting/c_abi`, and `log` is one of
the seven entries that ABI deliberately does not export). Lua, Python and Java
all reach `JceScriptHost::log`; C++ does not.

# Packaged-build verification pass (2026-08-16, later session)

**STILL NOT IN GIT.** Same as everything above. The engine/test fixes this pass
produced *are* committed and are listed at the end.

The consumer checked here is the **shipped runtime and the packaged build** —
not the editor and not loose files. That distinction is the whole point: the
publication policy dropped `.py` from packaged builds for months while the
editor kept running it fine from loose files.

## What was proved, and how

Every run below is `pak=yes loose=no` with **no `scripts/` directory beside the
exe**, so a script that loads can only have come out of the embedded archive.

### 1. The bytes really come back out of the PAK

The manifest listing a path proves nothing about its contents, so the archive
was deep-verified — `--verify` decompresses every entry and checks its content
CRC:

```
$ jce_pak --inspect ElementalSerenity_assets.pak --json bom.json --verify
$ python -c "...json..."
verify_ran : True
verified   : 91 / 91
corrupt    : 0
skipped    : 0
```

`skipped: 0` matters as much as `corrupt: 0` — a skipped entry is one that was
never checked, and "0 corrupt" over an unchecked set is silence, not evidence.

Note the release PAK has `has_debug_paths: false`, so BOM entries carry a
`path_hash` and a null `path`. The per-script proof is therefore the run below,
not a name lookup in the BOM.

### 2. `.class` deployment works — the shape a shipped Java game uses

ES ships Java **source**, which needs a JDK on the player's machine. A real
shipped game ships bytecode, which runs on a plain JRE. That path had never
been run here, so it was run:

```
$ javac -cp <java_classes>/classes -d <out> resources/assets/scripts/EsCampfire.java
$ xxd EsCampfire.class | head -1
00000000: cafe babe 0000 0041 ...
# copy into resources/assets/scripts/, scene scriptPath -> scripts/EsCampfire.class
$ cmake --build <build> --target ElementalSerenity      # 92 files packed (was 91)
$ ES_AUTOSHOOT=1 elemental_serenity.exe
```

```
app: runtime assets mounted: pak=yes loose=no
script: loaded 'scripts/EsCampfire.class' (java) for entity 642
[script] es_campfire (java) online: CampfireLight=ok CampfireLight2=ok probe=ok

java     scripts/EsCampfire.java             1     3705        2
```

Zero ERROR lines, `on_start` 1, both campfire lights resolved. **`.class`
deployment works end to end through the real cooker and the real packer.**

**The scene now points back at `scripts/EsCampfire.java` and the `.class` was
deleted.** It was compiled by hand and ES's build does not produce it, so
leaving it in `resources/assets/scripts/` would have left a stale artefact that
silently diverges the moment `EsCampfire.java` is edited. The permanent
protection is a committed repo test instead (see below).

**A REAL TRAP FOUND WHILE UNDOING IT.** Deleting the `.class` made the next
build fail:

```
ninja: error: '.../resources/assets/scripts/EsCampfire.class', needed by
  'ElementalSerenity_cook.stamp', missing and no known rule to make it
```

`jce_add_pak` collects cook inputs with `file(GLOB_RECURSE ... CONFIGURE_DEPENDS)`,
so **deleting an asset requires a CMake regenerate** (`cmake -S . -B <build>`)
before the next build will succeed. Adding one is fine; deleting one is not.

**AND THE HAZARD IT EXPOSED.** That failed build still left a runnable exe, and
running it printed a perfectly green `=== 4 of 4 languages live ===` — loading
`EsCampfire.class`, the file that had just been deleted, out of the stale PAK.
*A failed build prints green here.* Gate on the build exit code and the binary
mtime, never on the run.

### 3. The probe's `scriptPath` column is a label, not a measurement

While the scene pointed at `EsCampfire.class`, the probe table still printed
`scripts/EsCampfire.java`, because that column is a hard-coded literal in
`src/es_script_probe.c` and not the path the runtime actually resolved. The
counters (`on_start` / `on_update` / `resolved`) are real; **the path column is
the authored expectation.** Read `script: loaded '<path>' (<lang>)` from the log
when the question is *which file* loaded. Worth fixing if this probe is kept.

### 4. A packaged build missing a backend now says which case it is

Modelled by suppressing `jce_script_vm_python_register()` in
`src/es_script_langs.c` and rebuilding — the exe then genuinely has no Python.

Before (engine as it was):

```
script 'scripts/es_fireflies.py': no script VM claims its extension
  registered languages: java, lua, cpp
```

The word *python* never appears; the reader had to deduce whether the language
is unimplemented or merely unlinked. After the committed engine fix:

```
script 'scripts/es_fireflies.py' is python, and NO python BACKEND IS IN THIS
EXECUTABLE — this entity's script will NOT run, and it is NOT run as Lua.
  FIX: link scripting/python into this target and call
  jce_script_vm_python_register() at startup, BEFORE the first scene loads ...
  You do NOT need to write a VM: this engine implements python already.
```

The other branch was also run, with the scene pointed at `es_fireflies.rb`, and
correctly reports the extension as unknown to both registries — worded as two
possibilities, because `.escpp` is exactly a legitimate project-private
extension the catalog cannot know about.

`src/es_script_langs.c` was restored afterwards and the revert verified by
**sha256, not timestamp**.

## Attaching a script in the editor (2026-08-16, editor consumer pass)

Not committed either — this section documents editor behaviour that changed
under this project, so an ES author is not surprised by it.

**The Script component's asset picker now lists only files that can resolve to
a language.** It used to filter on `JCE_ASSET_KIND_SCRIPT` alone, and that kind
covers project code as well as scripts, so on this project the picker offered
20 entries of which 5 could actually be attached. The other 15 were `src/*.c`,
`src/*.h` and `src/es_flower_sway.cpp`.

`src/es_flower_sway.cpp` was the trap worth naming: it is genuinely this
project's C++ script, it is the file an author goes looking for, and attaching
it by path can never work — the cpp backend resolves the class name
`EsFlowerSway.escpp`, not a file. Picking it produced a Script component that

## The fifth entity

| entity | language | `scriptPath` | owns |
|---|---|---|---|
| `PropSurface` | **C** | `scripts/EsPropSurface.jcec` | `Rocks` / `Trees` / `Bridge` / `Camp` / `Tent` **MeshRenderer `baseColorR/G/B` + `roughness`** |

Source: `src/es_prop_surface.c`, compiled as C99 into `elemental_serenity.exe`
**and** into `es_scripts_c.dll` (the editor's copy — a SECOND entry in
`jce_project.json`'s `"script_modules"`, because one module descriptor is one
translation unit and a translation unit is C or C++).

### What the scene was missing, measured two ways

**1. Nothing in this scene ever got wet.** In a rainy state the pond splashes,
the rain emitter runs and the grass darkens — and the rocks, trunks, bridge
planks, fire-pit stones and tent canvas kept the exact albedo and the exact
`roughness` 1.0 they have in spring sunshine. **No script and no engine system
in this project has ever written `roughness` on any entity**, so this is not a
field taken from anyone.

**2. The seasonal stone tint was authored and reached nothing.**
`src/es_palettes.h` carries a `rocks_tint` for all eight states — winter's cold
`{0.875, 0.925, 0.975}`, autumn's warm `{0.925, 0.725, 0.525}` — and its only
consumer was, in `gen_director.py`:

```lua
ids.rocks = jce.find_by_prefix("rock")     -- lowercase r
for _, e in ipairs(D.ids.rocks or {}) do ... end
```

The entity `gen_scene.py` authors is named **`Rocks`**, and the host's prefix
match is a `strncmp` (`engine/src/application/jce_rt_script.c`,
`rt_find_prefix_cb`) — case sensitive. **That list has always been empty.**
Confirmed against pixels too: before this pass, a rock patch sampled at the
same coordinates read `212.1 212.9 199.5` in spring/day and `208.8 218.4 229.8`
in winter/day only because the *lighting* differed. After:

```
spring_day   rock patch mean RGB =  212.1  212.9  199.5
winter_day   rock patch mean RGB =  208.8  218.4  229.8   (blue-shifted)
autumn_day   rock patch mean RGB =  220.7  213.6  210.4   (warm)
rainy_day    rock patch mean RGB =   89.4  107.6  137.1   (wet + dark)
```

The dead loop and the `rocks_tint` column of the emitted Lua preset table are
**deleted** from `build/gen_director.py`, so exactly one script writes that
field. `rocks_tint` stays in `gen_director.py`'s `FIELDS` list — that list is
the **positional parse order** of `es_palettes.h`, and removing the row would
silently shift `leaf_tint` and `ground_tex` by three floats.

### Why C, honestly

Not speed. Five entities; the C++ flower script already holds the throughput
argument with 102.

* **`#include "es_palettes.h"`.** This project's application is C99 and its
  palette is a generated C header, so the C script reads the *same*
  `ES_PRESETS[8]` table `gen_director.py` parses, out of the same file, with no
  copy and no export step. No other language here can do that: Lua gets a
  generated transcription, and Python and Java would each need their own.
* **It costs nothing to ship.** Python needs an embeddable CPython; Java needs
  a JDK to build and a JVM plus `jce_script_java.dll` to run; the C++ script
  needs the C++ toolchain. A `.jcec` script needs the compiler that is already
  compiling `main.c`.

### How it knows which state the scene is in

It asks the director, by reading a component the director already writes:
`Ground`'s `MeshRenderer`, whose `albedoTex` is set per state to
`ES_PRESETS[i].ground_tex`. **The key and the payload come out of the same
struct row.** Polled at 4 Hz; the tint is chased with a 1.1 s time constant and
wetness rises with τ=3.5 s and falls with τ=14 s — an asymmetry no per-state
constant can express, which is why this needs `on_update` at all.

That is EsCampfire.java's pattern (read the director's live value rather than
writing a second copy of its state machine), not a private `is_raining()`.

**`Ground` is deliberately NOT in the prop list** even though it is the same
kind of surface: the director writes `Ground.albedoTex`, and `comp_set`
REPLACES a whole component. Two writers on one component is the one thing this
file forbids, and it would be invisible.

### How a C script patches a component from C

`comp_get` returns `cJSON_PrintUnformatted` output, so `es_json_splice()` walks
the string once, replacing the number after each of `baseColorR`, `baseColorG`,
`baseColorB`, `roughness` **in that order** and copying every other byte
verbatim. Sequential on purpose: a serializer that reorders its fields makes
the splice return 0 — a loud first-frame failure — instead of patching the
wrong number, and fields the script has never heard of survive untouched. It
writes only when a value actually moved (`1e-4`, well below one 8-bit colour
step), because a `comp_set` re-enters `jce_scene_set_mesh_renderer` and dirties
the renderer's per-entity caches.

### Evidence, and why a STILL value is proof

`src/es_script_probe.c` has a fifth row (`EsCProbe`) and `gen_director.py`'s
Lua read-out has a fifth row plus this:

```
ES probe c      Rocks baseColor = 0.2025 0.1725 0.0945  rough = 1.000
                (authored 0.6800 0.5700 0.3100 / 1.000)
```

`0.2025 0.1725 0.0945` is exactly `ES_PRESETS[1].rocks_tint` (spring/night, the
scene's authored state). The authored `Rocks` baseColor is `0.68 0.57 0.31`, and
**every** state's tint differs from it in every channel — so one sample read by
a different language proves the C script's `comp_set` landed, even in an editor
Play session that never presses a season button and never changes state. A
still value that is not the authored value proves as much as a moving one.

## The engine defects this pass found — COMMITTED (`6a5fb432`)

| # | defect | how it was found |
|---|---|---|
| 1 | **Two native script modules cannot be linked into one binary.** `JCE_C_MODULE_END` and `JCE_CPP_MODULE_END` both emit the shared-object entry `jce_cpp_script_module` unconditionally, and that is one external symbol: `LNK2005: jce_cpp_script_module already defined` + `LNK1169`. That is the shape `jce_script_vm_c.h` tells a five-language project to use, and it did not build. Fixed with `JCE_SCRIPT_MODULE_NO_ENTRY`, defined on the compile that goes INTO a binary; `tests/scripting/c/` now links two static C modules and the mutation is a **build failure**. | this project, the first time a C module was compiled beside the C++ one |
| 2 | **`MeshRenderer.visible` crossed JSON in NEITHER direction.** `parse_mesh_renderer` hardcoded `mr.visible = true` and read no key; `ser_mesh_renderer` wrote none — while GrassField, FoliageCluster, Water, TerrainChunk, VegetationScatter and BillboardRenderer all round-trip theirs. So the editor could not SAVE a hidden mesh, and any script's `comp_get` → modify → `comp_set` turned a hidden mesh back on. | **this project's own Lua director has never hidden a flower.** Magenta flower pixels, spring/day (authored visibility 1.00) vs winter/day (0.20): **1445 vs 1410 before**, `1444 vs 393` after |
| 3 | **The editor called a loaded C module a "C++ script module".** Five success messages said C++; the failure branch already said "native script module". A C author was told their module was something else *every time it worked*. Now "native", and the summary names both extensions. | the `2 of 2 loaded` line above, first run |

Defect 3 has **no automated gate** — the editor's log strings are not captured
