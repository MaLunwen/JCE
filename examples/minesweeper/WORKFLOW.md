# 面向项目用户的 AI / JCE 工作流

先描述玩法、目标设备和可修改范围，再选已有组件、SDK 服务和脚本语言。AI 用来编排、提案和检查，领域规则仍需可确定地验证。

1. **分析**：列出场景、组件、生命周期、存档与输入需求。先查公开 SDK／现有示例；发现通用能力缺口就留下最小复现、实际产物和影响，不在用户项目复制引擎实现。
2. **资源**：有联网工具的 agent 才能搜索和验证下载；模型能聊天或看图不等于能联网。当前 JCE LLM CLI 和本地网关没有搜索／工具调用能力，不能把模型编出的 URL 当成已发现的资产。
3. **资产复用**：记录原始页面、作者、许可证、文件哈希、修改步骤和目标格式，再经项目资产导入／cook。2026-09-22 查阅：[Kenney 官方说明](https://kenney.nl/support)的资产页资源为 CC0；[Poly Haven 许可](https://polyhaven.com/license)覆盖模型、贴图与 HDRI，网站内容和 API 另有条件。仍逐个核对实际下载包。
4. **自行创作**：找不到合适资源时可用几何原语或低面数模型先完成灰盒。一个可调整的起始预算是小道具 100–1000 三角面、1 个材质、512–1024 贴图；这只是项目预算建议，需在目标设备实测，不是引擎保证。先检查轴向、单位、UV、法线与简化碰撞体，再扩细节。
5. **场景创作**：使用 automation changeset 与实际组件 schema。小模型优先生成有限枚举／数值，可信工具映射到组件；大段整场景生成要检查未知字段、根／父子关系和引用，不只看退出码。
6. **驱动语言**：用脚本组合已有组件和服务。尽量让调参留在场景中；只把不可复用的游戏规则放进项目代码。编辑器 Play 和独立程序共用同一脚本入口。
7. **运行时 AI**：异步请求 → 提案 → 类型、范围、引用与预算校验 → 组件事务发布。按玩法选择立即或下一局生效；存档、回放记录提案版本。禁止将模型输出直接作为脚本执行。
8. **验证**：API 格式、回答质量、组件实际变化、画面和交互分别验证；打包前 cook，记录 SDK／程序版本。失败不自动重试到看似成功，要保存失败原因和新的测试条件。
9. **交付**：可运行包、场景与脚本、来源清单、可复现测试、编辑器／独立程序差异。新增引擎／编辑器问题用最小复现即时提出。

本扫雷示例使用引擎矩形与系统 UI 字体，没有下载第三方模型、贴图或音频；上面的资产流程是后续 3D 项目的工作建议。
