# JCE 证据与验证

本仓库最贵的错误不是写错代码，是**用一台坏了的仪器读数，然后把读数当结论**。
历史上有 24 条已记录的坏仪器；本轮又新增了 4 条，其中 2 条是我自己的。

## 0. 三步法（不可跳步）

```
① 先量噪声底      同一构建、同一环境，跑两次，量它们的差
② 只动一个变量    改动前后各一次，其余全部钉死
③ 带噪声底出结论  「差 X，噪声底 Y」；X 不显著大于 Y 就是没有结论
```

**噪声底必须在本次会话、本构建上实测。**
禁止引用工具文档里的历史值（如 0.0019%）当作本轮阈值——那是二手数字，
而且这棵树里至少有一个场景的噪声底是**双峰**的（三次里两次读 0.00000%，
一次读 3.2587%）。单次采样会以约 2/3 的概率给一个同分布的 A/B 发通行证。

## 1. 无头能力有两条轴，不是同义词（实测）

| 环境变量 | 后端 | 有像素吗 | 用途 |
|---|---|---|---|
| `JCE_HEADLESS=1` | bgfx **Noop** | **没有** | 纯逻辑/仿真。编辑器在此模式下 **exit 1**，日志 `jce_shaders: no shader suffix for renderer Noop` |
| `JCE_WINDOW_HIDDEN=1` | 真实 GPU | **有** | 一切像素验证 |

**任何像素验证都必须用 `JCE_WINDOW_HIDDEN=1`。** 拿 `JCE_HEADLESS=1` 去量
渲染或量 `sr_loop` 这类提交阶段，读到的是零。

## 2. 三条截图路径 —— 有两条绝不能混用（实测）

同一构建、同一环境（`JCE_MAX_FRAMES=150 JCE_DBG_FOCUS_SCENE=1 JCE_FRAME_DT_FIXED=0.016666 JCE_WINDOW_HIDDEN=1`）：

| 机制 | 语义 | 实测产物 |
|---|---|---|
| `JCE_CAPTURE_FRAME` + `JCE_CAPTURE_PATH` | 引擎 backbuffer，任何消费方可用 | PNG 1600×900 **3 通道** |
| `JCE_SHOT_FRAME` + `JCE_SHOT_PATH` | 编辑器 F12 的等价物（backbuffer） | PNG 1600×900 **3 通道** |
| `JCE_WINCAP_FRAME` + `JCE_WINCAP_PATH` | 整窗，走 **ImGui-FBO** | PNG 1600×900 **4 通道** |

实测差异（`read_png`，step=3 采样。**该函数现在的 owner 是 `tools/jce_determinism.py`**，`render_parity.py` 从那里 import）：

| 对比 | mean\|d\| | peak | %px>2 |
|---|---|---|---|
| 噪声底（`JCE_CAPTURE_*` 两次） | 0.6586 | 222 | 1.118% |
| 噪声底（`JCE_SHOT_*` 两次） | 0.4506 | 222 | 0.811% |
| **`JCE_CAPTURE_*` vs `JCE_WINCAP_*`** | **72.4678** | 255 | **88.338%** |

⇒ **`JCE_CAPTURE_*` 与 `JCE_WINCAP_*` 是两张本质不同的图，永不放进同一个 diff。**

⇒ **编辑器整幅画面的噪声底非零**：即使钉住 dt、焦点、隐藏窗口，仍有
mean 0.45–0.66、0.8–1.1% 像素在动。整幅 A/B 必须遮罩实时 UI 或改用区域判据。

⇒ **`peak` 在纯噪声里也是 222**。这个场景下 peak 不是判据。

⇒ **单次 md5 不相等不构成「两者不同」的证据**——同一路径自己两次运行 md5 就不同。

## 3. 确定性配方

```
JCE_FRAME_DT_FIXED=0.016666    # 必设。编辑器 Play 也认它
JCE_STREAM_SYNC=1
JCE_TAA_JITTER_PHASE=0
JCE_MAX_FRAMES=<N>             # 自动退出，且失焦时仍继续迭代
JCE_DBG_FOCUS_SCENE=1          # 或 JCE_DBG_FOCUS_GAME=1，二选一
JCE_MULTI_INSTANCE=1           # 见 §4
```

`JCE_DBG_FOCUS_*` **是必需的**：不设的话，被拍到的面板是 `imgui.ini` 上次留下的
标签页。历史上一次 `--play` 之后的三张后端截图全拍了 Game View，
Vulkan 与 GL 一致到 0.36 灰阶、两者都与 D3D11 差 56 —— 读起来完全像后端缺陷，
**其实是一个标签页**。（**两个都设会把两个视口都关掉**，不是后者被忽略：Scene View 的守卫是 `if (!s_dbg_focus_game && …)`、Game View 的是 `if (!s_dbg_focus_scene && …)`，互相把对方关掉。**必须二选一**——两个都设时截到的是空帧，而空帧和空帧比起来完全相等。）

## 4. 单实例锁会让一次运行静默作废（本轮实测）

第二个实例会激活已有窗口然后退出，**不渲染任何一帧**；调用方随后解析上一次的
日志/PNG，可能来自另一个构建。

- 现源码里 `allow_multiple_instances = e->headless || e->hidden_window || JCE_MULTI_INSTANCE`。
- **但 `hidden_window` 这条绕过是 2026-08-17（`67e91627`）才加的。**
  实测：一个 2026-08-14 构建的出货 exe **不认** `JCE_WINDOW_HIDDEN=1`，
  日志 `single_instance: single-instance lock already held` → `activated existing instance window` → **exit 1**，只产出 3 行日志。
- **规则：对任何已构建的产物做无头测量，一律显式加 `JCE_MULTI_INSTANCE=1`。**
  不要依赖 `JCE_WINDOW_HIDDEN=1` 兼带绕锁——那取决于产物的构建日期。
- `tools/perf_bench.py` 与 `tools/visual_diff.py` 都会在编辑器存活时拒绝启动；
  **`tools/envshot.py` 没有这个守卫**，不要在编辑器开着时跑它。

**引擎侧要加临时探针时**：走既有日志/trace 设施。一方代码里的裸 `fopen`
（及 `fread`/`fwrite`/`fclose`/`CreateFile`）与 `<pthread.h>` 会被
`check_engine_native_io.py` **直接拒收**，裸 `malloc`/`calloc`/`realloc`/`free`
会被 `check_raw_allocator.py` 拒收，「QA-only / debug-only」不豁免。

**但 `fprintf` / `getenv` / `printf` 没有任何门在拦**（2026-08-27 实测：两个检查器
里 `getenv|fprintf` 命中数都是 0，而引擎里就有 `SDL_getenv` 与一处裸 `printf` 活着）。
它们是风格禁令，不是机器判据——**别指望门替你拦，自己查**。

而且如果你的流程里没有 `python tools/lint/run_all.py`，被真正覆盖的那几类失败
会一路走到提交。

## 6. `perf_bench` 读数的两条硬规矩（本轮我自己踩的）

1. **perf 行必须取最后一条。** 它是 120 帧滚动窗口，前 120 帧是热身。
   我第一版脚本用「第一条匹配」，读出 `d3d12 34.61 ms / opengl 84.78 ms`，
   真值都是 **~6 ms**。整组跨后端对比因此完全作废。
2. **必须从日志断言 bgfx 实际选中的后端**（`jce_renderer: renderer: <X>`）。
   bgfx 会静默回落；「我设了 `JCE_BACKEND=x`」不等于「它跑的是 x」。
   断言后实测：`JCE_BACKEND=opengl` → **`OpenGL 2.1`**。

另：**GL 后端的 `gpu-mem` 恒为 0**（bgfx GL 无显存查询）。
该字段不能跨后端比较，也不能用 `gpu-mem=0` 推断「不占显存」。

`draws` 在多次运行间必须一致；不一致说明相机动了，几次运行不可比
（`perf_bench.py` 会就此告警）。

## 7. `.jirc` 输入回放的**真实作用域**（本轮实测，比传闻窄）

`JCE_INPUT_RECORD=<f.jirc>` 录、`JCE_INPUT_REPLAY=<f.jirc>` 放；两个都设时 replay 胜。

容器格式（权威 = `engine/src/os/platform/jce_input_record.c` 头注释）：

```
magic      "JIRC"   4 B
version    uint32   4 B  == 2
frame_size uint32   4 B  == sizeof(JceInputFrame) == 2336
_pad       uint32   4 B  写 0，读时要求为 0
frames     JceInputFrame[N]
```

`JceInputFrame` 偏移（`tests/os/platform/test_jce_input_frame_wire.c` 钉死）：
`version 0` / `key_count 4` / `keys_bits[64] 8` / `mouse_x 520` /
`mouse_buttons 540` / `touch_count 544` / `touches 552` /
`device_count 792` / `devices 800` / `sizeof 2336`。v1（stride 696）读时**升级**不拒绝。

**它能做什么**：驱动引擎侧 `JceInput` —— 动作映射、角色控制、手柄，可无头验证。

**它不能做什么**：驱动编辑器的 ImGui 热键。实测合成一个在第 120–126 帧按住
`JCE_KEY_F12`(=69) 的 `.jirc`，回放后 `~/.jce/screenshots` **一张都没多**，
阴性对照（全程不按键）同样是 0。机制：
`editor/src/core/jce_hotkeys.cpp` 的热键表键控在 **`ImGuiKey_*`** 上，
而 `editor/src/core/` 里 `jce_input_key|jce_input_pressed|jce_input_down`
的命中数是 **0** —— ImGui 的按键来自 SDL 事件，不经过 `JceInput`。

⇒ 编辑器热键（F9 / F12 / Ctrl+S / Ctrl+Shift+C）的无头替代品是 §2 的环境钩子。

⇒ **方法学**：两臂同为 0 时，差异为 0 分不清「信号不存在」和「通路不存在」。
必须去查机制。这一次阴性对照挡住了一次错误归因（差点去怪 `.jirc` 格式）。

## 9. 已知坏仪器（不完全清单，用前必读）

1. **`--rp` 曾经从不消融任何东西**：`.rp.json` 预设到不了编辑器视口管线。
   `--rp enable_csm=false` 只动了 144 px / 1.07 M，峰值 3 —— 阴影根本没关。
   修法是**同时**设 `JCE_RP_FORCE`。一个静默不消融的开关，会把
   「这个特性没有作用吗」从问题变成结论。
2. **`compare` 曾用均值印出「BIT-IDENTICAL」**：真实变化 4468 px / peak 13，均值 0.002。
   镜像式修法（「有一个像素不同就算变了」）同样错：同一构建两次就差 10492 px。
   现行规则：**一次比较只能独立断言一件事——一个像素都没变。其余都要带噪声底。**
3. **boot-inert 的 `--rp` 键**：`enable_taa`（改用 `--cvar r.taa=0`）、
   `shadow_resolution`、`csm_cascade_count`、`msaa_samples`、`render_scale`。
   渲染器的设置块是变更驱动的，boot 值永不触发。
4. **只写一个键的 `.rp.json`，其余键退回预设值**——解析器不是从清零的 desc 开始：`rp_parse_buffer()` 的注释写着 `out` 由调用方**预填 fallback preset**，`absent keys keep their preset value`。所以「其余全关」是错的，「其余回到预设」才对——预设是什么取决于调用路径（无 tier 时是 LOW）。
5. **被拍到的面板是继承状态**（见 §3 的标签页事故）。
6. **日夜时钟在启动期间就在走**，固定帧落到几点是启动耗时的函数。
   两张 17:30 与 17:54 写的截图曾字节相同（都跑进了夜里）。
7. **场景覆盖副本写错目录会静默破坏所有相对资产路径**，且仍然渲染得像模像样。
8. **闪烁残差随相机速度缩放**：同一 `--spin` 两次给出 11.40 与 14.40 px/frame（差 26%），
   造出一个 22.6% 的「渲染效应」，归一化后是 3.7%。比「每像素运动的残差」，不比原始残差。
9. **两次独立运行取出的一对不是一对**——shot frame 跨进程不对应同一个 spin 步。
   用一次运行内的 `--stride`/`--pairs`。
10. **空视口和另一个空视口比起来等于 0**：捕获在 250 步触发而场景需要 ~320 帧才起来，
    两侧都是 RGB(30,30,30)，门禁空过。
11. **整幅比较会被编辑器自己的实时文字淹没**：一次 Play 模式 A/B 整幅量得
    「peak 220、每帧都变」，差异全在控制台与性能面板那几行，视口里只有 135 px。
12. **`--crop` 两头都会切**：远级联轮转的差异在视口顶部一条窄带，
    裁到 `y >= 260` 就报 0.00000% —— 给一个真实改动发了通行证。
13. **`JCE_PERF_LOG` 是布尔不是路径**，目的地是 `JCE_LOG_FILE`。
14. **量化后再测量会毁掉测量**：先 `clip(v*4+128).astype(uint8)` 再算梯度，
    把四个不同的变体压进同一个桶报成字节相同，而它们的 PNG 有四个不同的 MD5。
15. **`graveyard` 与 `elemental_serenity` 在 `visual_diff` 配方下根本不重复**。
    先跑 `--floor-only`。

### 本机 Git Bash 里 `grep -c $'\r'` 是坏仪器（2026-08-27 实测）

对一个刚用 `printf 'a\nb\nc\n'` 造出来的**纯 LF 文件，它也返回 3**——匹配了每一行。
我据此判定「刚写的文件变成 CRLF 了」，差点回滚一次正确的编辑。

可靠替代：`tr -cd '\r' < file | wc -c`（应为 0），或 `head -1 file | od -c` 看字节。

同一轮还踩了第二个：`grep -c pattern f1 f2 ...` 多文件时输出 `file:count`，
用 `awk -F: '{s+=$2}'` 累加会被 Windows 路径里的 `C:` 打乱，得到 0。
**逐文件循环，或者用 `-h` 去掉文件名。**

### 用 shell heredoc 喂 Python 改文件时，转义层会静默改写你的内容

同一轮踩了**三次**，每次表现都不一样，且都不报错：

| 写的 | 实际到达 Python 的 | 后果 |
|---|---|---|
| `'    "79
"'` | 内含**真换行**，长度 9 而非 10 | 匹配 0 次，断言失败（这次是好的：写入前就停了） |
| `chr(92)+'r'` 那类字面 `\r` | **真 CR 字节** | 写进文件，再被 `read_text()` 的通用换行读成换行，**把两行劈开** |
| 未转义的 `` `ck` `` | 被当**命令替换**执行，替成空串 | 文本里凭空少了一个词，`check_skills` 查不出来（它只查名词存在，不查句子是否成立） |

**规避**：
- heredoc 一律用**引号形式** `<<'PY'`（禁止 shell 展开）；需要传路径就用环境变量。
- 需要写字面反斜杠时用 `chr(92)`，不要靠层层转义。
- 改完**读回来验一眼**，别只信「脚本说 OK」——第三次就是脚本报了成功。

两次都印证 §0：**先用一个已知答案的对照物验仪器，再用它下结论。**

### 门禁的失败闸门卡在中间 ⇒ 它后面的检查全是死的（2026-08-27 自查照出）

`check_determinism_contract.py` 的

```python
if failures:
    print(...); return 1
```

原本卡在文件中段。它**后面**还有两节：空帧守卫的合成测试、以及环境变量读者
检查。那两节里每一句 `fail()` 都被收进了一个再没人读的列表——门禁看起来在跑，
实际上永远不会因为它们而红。两条阴性对照连着两次返回 exit 0 才把它揪出来。

**判据：失败闸门必须是 `return 0` 之前的最后一件事。** 写完一个检查，
立刻用阴性对照验证它**真的会红**；只验证「基线是绿的」等于什么都没验证。

### 共享了守卫，没共享喂给它的东西（同一族的第 N 次）

`assert_has_content` 搬进 `jce_determinism.py` 时，它**唯一的输入生产者**
`read_png` 留在了 `render_parity.py` 里。结果：守卫是共享的，但任何第三个调用
者都拿不到能喂给它的东西——「正确的共享实现 + 零可达调用者」。
搬函数时**连它的输入生产者和 import 一起搬**（这次 `import struct` / `zlib`
没跟着走，第一次调用就 `NameError`）。

### 「某物存在」不能用子串测，因为 import 行会满足它

第一版写成 `if "assert_has_content" not in src: fail(...)`。
`from jce_determinism import assert_has_content` 这一行就满足了它，
**把全部调用点删光仍然 exit 0**。要数**调用点**（排除以 `from` / `import`
开头的行），不要数名字出现过没有。

### 出货件开没开监听口，用 OS 的套接字表量，别靠推断

```powershell
$p = Start-Process -FilePath <exe> -PassThru
Get-NetTCPConnection -State Listen | Where-Object { $_.OwningProcess -eq $p.Id }
Get-NetUDPEndpoint            | Where-Object { $_.OwningProcess -eq $p.Id }
```

回环（`127.0.0.1` / `::1`）**不触发** Windows 防火墙弹窗，`0.0.0.0` 触发。
两者在 `boot` / `screenshot` / `perf` 里长得**完全一样**——带公网监听口的包
照样启动、照样渲染、照样出数。详见 `user-project-sdk.md` §5c。

### 复核一条断言时，量的必须是**那条断言**，不是它旁边那个好量的东西

2026-08-28 实测：skill 写「加一个编辑器面板要改 `jce_editor_layout.cpp` 内的 **6 处**」。
我 `grep -c 'JCE_PANEL_WORLD_STREAMING'` 读到 **3**，差点把一条正确的条目判成过时并改掉。

真相：那 6 处是 **6 类接线**，只有 3 类含枚举记号，另 3 类用字符串
`"###world_streaming"` 与 `window.worldStreaming`。**断言说的是「类」，我数的是「记号」。**
把行 `grep -n` 出来读一眼，六类全在，行号与文档一字不差。

同一族的其它形态（本仓库都出现过）：
- 断言是「守卫会拒绝 X」，而我量的是「基线是绿的」——**只验基线等于什么都没验**
- 断言是「某函数被调用」，而我量的是「某名字出现过」——**import 行就能满足**
- 断言是「这个包在跑」，而我量的是「打包命令 exit 0」——**包装器的退出码不是被包装物的**

**判据：先把断言改写成一句可证伪的话，再问「我这条命令的输出，能不能把它证伪」。**
不能证伪它的输出，读到什么都不构成复核。

### 「一端渲染正常、另一端空白、两端都不报错」⇒ 先怀疑 bgfx view id 撞了

bgfx 的 view 状态是 **last-write-wins**，view 顺序是一次**全局重映射**。
两个子系统拿同一个 view id **不会冲突报错**——一方静默停止出像素。

真实形态：编辑器 ECS-UI Canvas 覆盖层坐在场景渲染器的动态 CSM 频段上，
每帧画进一个随后被颜色 pass 清掉的目标，**两个编辑器视口全空、出货运行时正常，
不报错不打日志**。查渲染逻辑查不出来——归属表在
`engine/include/jce/renderer/jce_views.h`，门是
`python tools/audit/check_view_reservations.py`。详见 `architecture-map.md`。

## 9b. 「读回来对了」不等于「恢复对了」——多走一步（2026-09-01 实测）

存档 / 反序列化 / 撤销恢复这一族，最自然的测试形状是

```
写入 → 读回 → 断言读回的值 == 写入的值
```

**这个形状会在被测物仍然坏着的时候通过。** 它只验证了「状态被写进去了」，
没有验证「系统会接受这个状态继续运行」。

实测：环境存档恢复了小时（20:00），断言当场通过。但推进器靠
`day_seed_hour`（= 已消费的**授权**种子）判断设计师有没有改过滑条；
我的读回调把它设成了**恢复后的活小时**，于是下一帧授权的 08:00 与它不等，
推进器判为「设计师改了」重新播种，**读档被弹回关卡开头**。
期望 21.00，实得 9.00 —— 而只断言读回值的那一版测试是绿的。

⇒ 定则：**恢复类测试必须在读回之后再推进至少一步**，再断言。
一步就够——错的状态几乎总是在第一次前进时暴露，因为「恢复」和「继续」
用的往往是两套不同的判据。

同族：反序列化后再存一次、撤销后再做一次编辑、加载后再跑一帧物理。

## 9c. 稠密表里的 0 不是「跑得快」，是「没跑」（2026-09-01 实测）

`JCE_KPI_FRAME_LOG` 写的是**稠密**表：每一个已注册阶段、每一帧都有一行。
所以某一帧没跑到的阶段贡献的是 `0.0000`——**前两帧整片是 0**，因为阶段是
首次使用时才注册的。

把这些 0 放进同一个百分位，等于把「没跑」和「跑了 0 毫秒」平均在一起，
答的是没人问过的问题。**取百分位时按「该阶段真正跑过的帧」取。**
这不会掩盖「某阶段不再运行」——那应该由「预算点名的阶段在这次捕获里从未出现」
这条发现来抓，两者是不同的判据。

**暖机要量，不要假设。** 同一次 150 帧捕获：

| 阶段 | 含全部帧 p95 | 跳过前 20 帧 p95 |
|---|---|---|
| `scene_render` | 8.026 ms | **7.472 ms**（7% 是启动） |
| `draw_submit` | 4.066 ms | 4.066 ms（**不受影响**） |

后一行才是有用的那半：**暖机不会污染每一个阶段**，所以一刀切地跳过是一次
*修正*而不是一个假设——要说得出它在这次数据上移动了多少。

**清洗之后必须重跑阴性对照。** 「让数字更干净」正是把检查掏空的高发时刻。

## 9d. 相机里没有被测物 —— 三种形状，守卫全都没拦（2026-09-08 实测）

**一整场 SSGI 战役（十二次捕获、一次阳性对照、三份 shader 诊断、一个写完又
撤销的降噪器）跑在一个相机从未包含过被测物的 fixture 上。** 每个数字都是真的，
每条结论都是错的。三个原因叠在一起，任何一个单独出现都足够：

| 形状 | 症状 | 判据 |
|---|---|---|
| **场景的 `contract` 块是自造的** | 加载器打印「4 entities」，**一个都不画** | `contract` 必须逐字是 `{"name": "jce.scene", "major": 1, "minor": 0}`；抄一份已知能画的场景，别自己发明 |
| **`--pitch` 取了负数** | 相机在目标**下方朝上看**；天空和网格填满画面 | envshot 里**正 pitch 才是俯视**（forest 42 / canopy 38 / slope 32；只有 `sky` 是 -22） |
| **`rendering` 块缺 `sky`/带浓雾** | 几何画了，但 22 m 外被雾洗成纯白 | 从 `hidden_cove.scene.json` 的 `rendering` 抄，只改要改的键 |

**守卫是存在的，而且它没有运行。** `assert_subject_in_frame` 读的是引擎的
stdout，而 `tools/envshot.py` 过去**只在给了 `--log` 时才保留 stdout**，
于是每次捕获都打印这一行然后继续：

```
[envshot] subject-in-frame NOT verified (pass --log; a capture aimed at
empty space is not blank and no image guard can tell)
```

**一道只在你主动打开时才运行的门，等价于没有门。**
已在 `tools/envshot.py` 修好：`--log` 默认写 `build/envshots/<name>.log`，
两道守卫（后端 + 被测物）每次捕获都跑，日志缺失是硬错误而不是跳过。

**但它仍然只数「过了视锥的实体」，不数像素。** 实测：相机在地面之下朝上看时，
它照样报「3 visible entities」。所以：

> **每个新 fixture 的第一张图必须用眼睛看过**（裁到视口另存一张小图再 Read），
> 之后才允许开始度量。像素统计不会告诉你画面里是天空。

配套：一张图「不空白」「有内容」「噪声底是 0」全都可以在**没有被测物**时成立——
噪声底为 0 恰恰是因为画面里什么都没动。**极低的噪声底是可疑信号，不是好消息。**

## 9g. 两个被对照打死的假设，都是我先写成事实的（2026-09-22 实测）

编辑器和出货 exe 的同一帧，**53% 的像素不同**，其中绝大多数是棋盘上 ±1 LSB、
而且**双向**（game 59 -> editor 60 和反向一样多）。

**假设一：TAA 地板。** 两个 host 各跑各的 jitter 序列、各自的历史，平坦表面收敛到
同一个颜色但落在相邻的 8 位值上。这解释了所有观察，听起来无懈可击，
**我把它当作事实写进了 `pixel_diff` 的 docstring**。

对照：**同一个二进制跑两遍**。结果 **0 / 921,600，最大通道差 0**。
再跑一遍、截图时刻**差一帧、差两帧**：**还是 0**。
⟹ 游戏对截图相位是逐位确定的，**根本没有 TAA 地板**，
那 45 万个 ±1 像素每一个都是两个 host 之间真实且可复现的差异。

**假设二：时序。** 编辑器第 30 帧才进 Play，所以截图抓到的是同一局游戏的不同时刻。
这一条**是真的**（蛇在编辑器里多走三格，修掉了），但它**不是** ±1 的原因：
换成**静止帧**（全程不按 ENTER，停在 MENU，画面完全不动）之后，
差异**没有变小**（53.30%）。

真相是几何：沿墙边做亚像素边缘拟合，**编辑器把棋盘画矮了 2.4%**
（game 687.16 px 壁到壁，editor 671.01，三个采样列一致到 ±0.01 px）。
同一张画、同样的布局和颜色，**投影不同**。

### 可执行的结论

1. **任何「这个差异是噪声/地板」的说法，先跑同一个二进制两遍。**
   它便宜、它是阳性对照、而且它**可能直接推翻你正要据以放宽判据的那个机制**。
   一个「由看起来正确的机制论证出来的容差」会把这整件事判成绿的。
2. **把对照做成 harness 的一部分，而不是一次性实验。**
   `parity.py` 现在每个场景都多跑一趟游戏，判据是
   「编辑器与游戏的差异 ≤ 游戏与它自己的差异」——
   地板每次重测，而不是某个人某一天定下的常数。
3. **先取一帧「时间无关」的画面**（本例是 MENU 静止帧）。
   它把「两边画得一样吗」和「两边的钟对齐吗」分开；
   在像素计数里这两种失败**长得完全一样**。
4. **写下机制之前先跑对照。** 我这次是反的：先把 TAA 写进 docstring，
   再跑对照，然后必须回去改掉那段话。
   见 [[jce-a-written-reason-outlives-its-truth]] 同族。

## 判据的第三种结论：WITHHELD

PASS / FAIL 两档不够用，而硬凑成两档会**把关于环境的事实说成关于被测物的事实**。

2026-09-20 一天里四处需要它：

| 场合 | 两档会怎么说谎 |
|---|---|
| 并发测试里子进程起不来（提交量耗尽） | 报 FAIL ⟹ 读成「并发串台了」，而串台根本没被测到 |
| `visual.measure` 的前置条件不满足（画面里没有被测物） | 报 FAIL ⟹ 读成「构图不合格」，而那张图压根不含被测物 |
| 音频测试遇到 `audiodg` 崩了 | 报 FAIL ⟹ 读成「引擎音频坏了」；报 IGNORE ⟹ 读成「这台机器没有声卡」。**两个都不对** |
| 验证脚本里每一次调用都返回 `INTERNAL` | 拿错误和错误比 ⟹ 打出「两个对照都过」 |

**规则：当前置条件不满足时，扣住判决并说出扣住的理由，不要给 PASS，也不要给 FAIL。**
特别是：**一个守卫如果从构造上无法区分「设备不存在」和「设备存在但坏了」，
它就不该只有 ignore 一个出口**——两种情况对被测物的意义完全相反。

写法上的两个配套：

- **任何计数断言之前，先断言前置条件成立**（桩被调用过、序列跑通过、图里有被测物）。
  否则「前置条件没满足」会伪装成一个**数字**，而不是一条明确的失败。
- **扣住的那一条也要计入输出**，不能静默跳过——静默跳过和通过在汇总行上逐字相同。

## 9e. 控制组可以**正确地红**，而它怀疑错了对象（2026-09-20 实测）

一个阳性对照红了，信息量很大——但它只告诉你「这里不对」，**不告诉你哪里**。

实测：一个自由刚体在 3 N·m 反向力矩下真实转了约 **−36 rad**，而读数是 **+1.9991**，
于是对照断言「负载从来没到达」并红了。负载一直在到达；
**回绕的是仪器**：`2*atan2(z, w)` 只在 (−2π, 2π] 上单值。

两条可迁移的话：

1. **对照红了，先问「它测的那个量还成立吗」，再去改被测物。**
   我当时的下一步差点是去调马达强度——那会把一个正确的实现改坏，
   而对照仍然会红，因为仪器没动。
2. **修法通常是换量，不是调阈值。** 速度马达命令的是**角速度**；
   角速度不回绕，而且它就是被命令的那个量。换量之后六个用例的数字
   全部与命令值吻合（2.0000 rad/s、±2.0000、−35.9999 …），
   阈值反而不再重要了。

同族：`2·acos(|w|)` 在 180° 附近对转轴不敏感（2026-08-24）。
**任何从四元数里读角度的量，先问它的单值区间是多少。**

## 9f. 一条断言可以在它要抓的缺陷面前**一直是绿的**（2026-09-20 实测）

`test_jce_configurable_joint` 的 limited-axis 用例断言两件事：
「分离量从不显著超过 L」「比自由参照更受约束」。
**两条对一个 LOCKED 轴同样成立**（分离量 ≈ 0）。
而 `cfg_apply_axis` 恰好把 LIMITED 落进了 LOCKED 分支——
**这个用例为它要抓的那个缺陷绿了整整一段历史。**

用例作者自己写下了线索，措辞是「限位轴在范围内的自由滑动是另一个细节，见 followups」——
那个被推迟到 followup 的「细节」，**正是区分 LIMITED 与 LOCKED 的唯一性质**。

⇒ 两条判据：
- **写一条断言时，问「被测物坏成什么样，它还会绿」**；如果答案是「坏成另一个合法状态」，
  它测的就不是它名字说的那件事。
- **修好缺陷之后补的断言，必须再把缺陷放回去跑一次。**
  没跑过的新断言与它替换掉的那条空洞断言，在绿色里长得一模一样。
